# Task File Format Reference

This document defines the task file format used in the bonuscompplatform project. All task files generated by `/waypoint.plan-gaps` must follow this format.

## Naming Convention

```
task-{NNN}-{kebab-case-slug}.md
```

- NNN: Three-digit zero-padded number (001, 002, 012)
- slug: Kebab-case derived from the task name (e.g., `hide-approve-buttons-wrong-approver`)
- Continue numbering from the highest existing task in the target folder

## File Structure

```markdown
# Task NNN: [Task Name]

**Plan**: [path or "N/A — UAT gap fix"]
**Spec**: .waypoint/specs/[feature].md
**UAT Report**: .waypoint/uat/[report].md
**UAT Issue**: Issue N — [title]
**UAT Scenario**: TS-NNN
**Phase**: Fix
**FR**: [FR-N, FR-M] or N/A
**Depends**: none | task-NNN, task-MMM
**Estimated effort**: Small | Medium | Large

## Context

This task addresses a gap identified during UAT Run N.

- **UAT Report**: `[path]`
- **Issue**: #N — [title]
- **Severity**: Critical | Major | Minor
- **Original Scenario**: TS-NNN — [scenario name]

## Objective

[1-2 sentence clear description of what needs to change]

## Acceptance Criteria

- [ ] [Criterion derived from UAT Expected behavior]
- [ ] [Additional criteria from root cause analysis]
- [ ] Existing tests continue to pass
- [ ] Re-run UAT scenario TS-NNN confirms the fix

## Files to Modify

- `path/to/file.ts` — [what to change]

## Files to Create (if needed)

- `path/to/new-file.ts` — [purpose]

## Implementation Notes

[Specific guidance: function names, component names, patterns to follow]

## Testing Requirements

- [ ] [Specific test cases]
- [ ] Re-run UAT scenario TS-NNN
```

## Priority Mapping

| UAT Severity | Task Priority | Rationale |
|-------------|--------------|-----------|
| Critical | P0 | Security vulnerability or data loss |
| Major | P1 | Broken functionality, affects users |
| Minor | P2 | UX improvement, cosmetic issue |

## Effort Estimation

| Effort | Typical Scope |
|--------|--------------|
| Small | Single file change, < 20 lines, clear fix |
| Medium | 2-3 files, some refactoring, new logic needed |
| Large | Multiple files, new component/pattern, complex testing |

## Manifest Entry Format

When adding to `waypoint.manifest.yaml`:

```yaml
documents:
  tasks:
    {feature-name}:
      # ... existing tasks ...
      - path: .waypoint/tasks/{feature-name}/task-{NNN}-{slug}.md
        status: pending
        summary: "One-line description of the fix"
        depends: []
        fr: []
```

## Example: UAT Gap Fix Task

```markdown
# Task 039: Hide Approve/Return Buttons for Non-Current Approver

**Plan**: N/A — UAT gap fix
**Spec**: .waypoint/specs/compensation-dashboard-overview.md
**UAT Report**: .waypoint/uat/comp-dashboard-lifecycle-2026-04-09-1600.md
**UAT Issue**: Issue 1 — Approve/Return buttons visible to wrong approver
**UAT Scenario**: TS-036
**Phase**: Fix
**FR**: N/A
**Depends**: none
**Estimated effort**: Small

## Context

This task addresses a gap identified during UAT Run 2.

- **UAT Report**: `.waypoint/uat/comp-dashboard-lifecycle-2026-04-09-1600.md`
- **Issue**: #1 — Approve/Return buttons visible to wrong approver
- **Severity**: Minor
- **Original Scenario**: TS-036 — Wrong approver cannot approve

## Objective

Hide the Approve and Return for Revision buttons on the approval review page when the
current user's email does not match the current approval step's approver email. The
server-side guard already blocks the action (returns 403), but the buttons should not
be visible to prevent user confusion.

## Acceptance Criteria

- [ ] Approve and Return buttons are hidden when user email !== currentStep.approverEmail
- [ ] Approve and Return buttons remain visible when user email === currentStep.approverEmail
- [ ] Server-side guard (403) still works as a defense-in-depth measure
- [ ] Existing approval tests continue to pass
- [ ] Re-run UAT scenario TS-036 confirms buttons are hidden for wrong approver

## Files to Modify

- `bcp-web/components/approvals/pages/approval-review-page.tsx` — Pass user email and
  current step approver email to DecisionCard
- `bcp-web/components/approvals/decision-card.tsx` — Accept `isCurrentApprover` prop
  and conditionally render buttons

## Implementation Notes

The approval review page already has access to the workflow data including `currentStep.approverEmail`.
The authenticated user's email is available from the auth context. Compare them (case-insensitive)
and pass a boolean to DecisionCard.

## Testing Requirements

- [ ] Unit test: DecisionCard hides buttons when isCurrentApprover=false
- [ ] Unit test: DecisionCard shows buttons when isCurrentApprover=true
- [ ] Re-run UAT scenario TS-036
```
