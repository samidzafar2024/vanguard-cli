<methodology>
**1. WebSocket Endpoint Discovery**
Use Task agents to find all WebSocket endpoints in the codebase:
- Search for `new WebSocket(`, `io(`, `pusher`, `cable`, `sockjs`, `socket.io` in frontend code
- Search for `ws://`, `wss://` URLs
- Check server-side for WebSocket upgrade handlers
- Review package.json/go.mod for WS libraries (socket.io, ws, gorilla/websocket, etc.)

**2. Authentication Analysis**
For each WebSocket endpoint, answer:
- Is the HTTP Upgrade request authenticated (cookie, token, query param)?
- Is token validation done at connection time or per-message?
- Can an unauthenticated WebSocket connection be established?
- Are connection tokens validated server-side or just checked client-side?

**3. Authorisation Analysis**
For each channel/room/namespace:
- Can a user subscribe to another user's private channel?
- Is channel authorisation re-validated on reconnect?
- Can a user send messages to channels they're not subscribed to?
- Does the server validate the sender identity in message payloads?

**4. Origin Validation**
```bash
# Test WebSocket with spoofed Origin header (if wscat available)
wscat -c "wss://{{WEB_URL_DOMAIN}}/ws" \
  --header "Origin: https://evil.com" \
  --header "Cookie: session=VALID_TOKEN" 2>&1 | head -20
```
Check source code for `allowedOrigins` or CORS-equivalent origin checks on WS upgrade.

**5. Message Tampering**
For authenticated channels, test whether:
- Message `user_id` or `channel` fields can be manipulated
- Subscription events can reference other users' IDs
- Broadcast events accept arbitrary targets

**6. Replay Attack**
- Are WebSocket messages signed or contain anti-replay tokens?
- Can captured messages be replayed to trigger actions?

**7. Rate Limiting**
- Is there per-connection or per-message rate limiting?
- Can a single connection flood the server with messages?

**8. DoS / Resource Exhaustion**
- Maximum connection limits per user?
- Memory exhaustion via large message payloads?

**Vulnerability Classification:**
For each finding, determine:
- `externally_exploitable`: true only if exploitable without internal access
- `confidence`: high | med | low
- `witness_payload`: the exact WebSocket message or connection request to demonstrate the flaw
</methodology>
