<scope>
Focus exclusively on AWS-specific attack surfaces:
- IAM roles, policies, and permission boundaries (privilege escalation paths)
- S3 buckets: public access, ACLs, bucket policies, object-level permissions
- AWS Lambda: function URLs, resource-based policies, environment variable leaks
- ECS/EKS: task role permissions, container metadata endpoint exposure
- EC2: instance metadata service (IMDSv1 vs IMDSv2), security group open ingress
- CloudFormation/CDK/SAM: IaC misconfigurations and hardcoded secrets
- AWS Secrets Manager / Parameter Store: overly permissive access
- SSRF to AWS metadata endpoint (`169.254.169.254/latest/meta-data/`)
- Cognito: misconfigured identity pools, unauthenticated role over-permissions
</scope>

<systematic_approach>
Work through the following steps. Skip steps where tools are unavailable — document the skip with a reason.

**Step 1 — Catalogue Prior Cloud Findings**
Read cloud_security_deliverable.md and extract:
- All S3 bucket names, Lambda ARNs, ECS/EKS cluster identifiers
- Any IAM role ARNs or policy documents discovered
- Hardcoded AWS credential prefixes (`AKIA`, `ASIA`, `AROA`)
- IaC file paths (*.tf, *.yaml CloudFormation, serverless.yml)

**Step 2 — IAM Deep Analysis**
Analyse all IAM policies found in IaC for dangerous patterns:

```bash
# Find all IAM policy documents in the repo
find {{REPO_PATH}} -maxdepth 8 \( -name "*.tf" -o -name "*.json" -o -name "*.yaml" -o -name "*.yml" \) \
  | xargs grep -l '"Action"\|resource.aws_iam\|iam:' 2>/dev/null | grep -v ".git" | head -20

# Detect wildcard permissions and admin roles
grep -rn '"Action": "\*"\|"iam:PassRole"\|AdministratorAccess\|PowerUserAccess' \
  {{REPO_PATH}} --include="*.tf" --include="*.json" --include="*.yaml" 2>/dev/null | grep -v ".git" | head -30

# Find privilege escalation paths: iam:CreatePolicyVersion, iam:AttachUserPolicy, etc.
grep -rn 'iam:CreatePolicy\|iam:AttachUserPolicy\|iam:AttachRolePolicy\|iam:PutUserPolicy\|iam:SetDefaultPolicyVersion' \
  {{REPO_PATH}} 2>/dev/null | grep -v ".git" | head -20
```

**Step 3 — S3 Exposure Check**
For each S3 bucket name found in Step 1, test public accessibility:

```bash
# Test public bucket listing (replace BUCKET_NAME with discovered names)
curl -s -o /dev/null -w "HTTP %{http_code}" "https://BUCKET_NAME.s3.amazonaws.com/" 2>/dev/null

# Check for public objects via path-style URL
curl -s -o /dev/null -w "HTTP %{http_code}" "https://s3.amazonaws.com/BUCKET_NAME/" 2>/dev/null

# Test for directory listing with known prefixes
curl -s --max-time 5 "https://BUCKET_NAME.s3.amazonaws.com/?list-type=2&max-keys=5" 2>/dev/null | head -30
```

**Step 4 — SSRF to AWS Metadata**
Test whether the target application proxies or reflects the AWS instance metadata endpoint:

```bash
# Direct metadata via common SSRF vectors (use vanguardFetch with WAF bypass settings)
# Test each path below via known SSRF injection points identified by the recon agent

# IMDSv1 — returns instance metadata if vulnerable
curl -s --max-time 5 "{{WEB_URL}}/latest/meta-data/" 2>/dev/null | head -20

# Common SSRF parameter names — probe one at a time, check for "ami-id" or "iam/" in response
for param in url redirect callback src proxy target fetch webhook; do
  resp=$(curl -s --max-time 3 "{{WEB_URL}}?${param}=http://169.254.169.254/latest/meta-data/" 2>/dev/null)
  if echo "$resp" | grep -q "ami-id\|iam/\|instance-id\|security-credentials"; then
    echo "SSRF FOUND via param: $param"
    echo "$resp" | head -20
    break
  fi
done
```

**Step 5 — Lambda and ECS Exposure**
For Lambda function URLs or ECS task metadata endpoints identified in prior deliverables:

```bash
# Lambda function URLs are of the form: https://<id>.lambda-url.<region>.on.aws/
# Test any discovered Lambda URLs for unauthenticated access
# curl -s --max-time 5 "<lambda_url>" | head -20

# ECS task metadata — accessible from inside containers only; check IaC for exposed task roles
grep -rn 'ECS_ENABLE_TASK_IAM_ROLE\|169.254.170.2\|taskRoleArn\|executionRoleArn' \
  {{REPO_PATH}} 2>/dev/null | grep -v ".git" | head -20
```

**Step 6 — Cognito Misconfiguration**
Search for Cognito identity pool and user pool references:

```bash
# Find Cognito pool IDs in source code and IaC
grep -rn 'cognito\|IdentityPoolId\|UserPoolId\|us-east-1:[a-f0-9-]\{36\}' \
  {{REPO_PATH}} --include="*.ts" --include="*.js" --include="*.json" --include="*.tf" 2>/dev/null \
  | grep -v ".git" | head -20
```

**Step 7 — Hardcoded Credentials Deep Scan**
Go beyond the secrets-detection deliverable with AWS-specific patterns:

```bash
# AWS Access Key IDs: start with AKIA (long-lived) or ASIA (temporary)
grep -rn '\bAKIA[0-9A-Z]\{16\}\b\|\bASIA[0-9A-Z]\{16\}\b' \
  {{REPO_PATH}} 2>/dev/null | grep -v ".git" | head -20

# AWS Secret Access Keys: 40-char base64-like strings near "secret" keywords
grep -rn 'aws_secret_access_key\s*=\s*[A-Za-z0-9+/]\{40\}' \
  {{REPO_PATH}} --include="*.env*" --include="*.tf" --include="*.yaml" 2>/dev/null \
  | grep -v ".git" | head -10
```
